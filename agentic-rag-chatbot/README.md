# Phase 5: Agentic RAG Orchestrator

This module implements Phase 5 (Agentic RAG Orchestrator) of the Plug-and-Play Agentic RAG Chatbot. It acts as the central intelligence hub, taking normalized user queries, determining intent, planning a sequence of tool calls, evaluating evidence, and gating the handoff to Phase 6 (LLM Integration).

## Core Features

- **Strict Validations & Limits:** Enforces hard boundaries on context sizes (`MAX_TOP_K`), iteration steps (`MAX_TOOL_CALLS`), and similarity thresholds (`MIN_RELEVANCE_SCORE`).
- **Tools Registry:** Supports secure, identity-aware Vector Search (Phase 4), Structured Query backend integrations (Phase 4), and a strictly bounded AST-based Calculator.
- **Handoff Gate:** Evaluates the gathered `OrchestratorContext` and blocks the LLM from hallucinating by short-circuiting to a "Clarification" or "Failure" state if insufficient evidence is gathered.
- **Resilient Phase 4 & 6 Clients:** Highly optimized HTTPX clients with precise status mapping, secure internal authentication propagation, and exact-retry logic for connection errors.
- **Structured JSON Logging:** Outputs fully parsed JSON summary telemetry for every turn.

## Installation & Setup

1. **Prerequisites:** Python 3.10+
2. **Install dependencies:**
   ```bash
   pip install -e .
   ```
   *(For development/testing, install `pip install -e .[test]`)*

## Environment Configuration

The orchestrator relies on the following environment variables (defined in `app/config.py`):

| Variable | Default | Description |
|---|---|---|
| `PHASE4_BASE_URL` | `http://localhost:8004` | The internal endpoint for Phase 4 Retrieval. |
| `PHASE4_TIMEOUT_MS` | `5000` | Timeout in ms for Phase 4 requests. |
| `PHASE6_BASE_URL` | `http://localhost:8006` | The internal endpoint for Phase 6 LLM handoff. |
| `PHASE6_TIMEOUT_MS` | `10000` | Timeout in ms for Phase 6 requests. |
| `INTERNAL_SERVICE_TOKEN` | *(Required)* | The service-to-service authentication token. |
| `MIN_RELEVANCE_SCORE` | `0.5` | The minimum chunk score to include in the context. |
| `INCLUDE_TOOL_RESULTS` | `False` | Whether to pass calculation/structured data to Phase 6. |

*(There are also additional execution limits such as `MAX_RETRIEVAL_ATTEMPTS`, `MAX_TOOL_CALLS`, etc., that default to safe limits).*

## Testing

The project uses `pytest` and `httpx_mock` to validate strict contract compliance against Phase 4 and Phase 6, as well as Phase 2 Identity structures.

Run the test suite:
```bash
python -m pytest
```

## Integration Instructions

1. **Phase 2 (Identity):** The input `Identity` model strictly expects `user_id`, `tenant_id`, `roles` (list of strings, strictly `"user"` or `"admin"`), and `session_id`.
2. **Phase 4 (Retrieval):** The `RealPhase4Client` correctly forwards identity parameters along with the internal service token via the `X-Internal-Auth` header. 
3. **Phase 6 (Generation):** Context generated by Phase 5 matches exactly the `OrchestratorContext` schema required by Phase 6, and respects all authentication limits without logging sensitive internal HTTP tokens.
